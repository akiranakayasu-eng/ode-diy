## 自分で行った確認

1. **ARM 版の作り直し**: 置いてある `build/ode_main.bin`（194,480 バイト）と同じ大きさで、違いは 3 バイト（`__TIME__`）だけ。置いてある hex は今のソースから作ったものと見てよい。`app/` の警告なし。
2. **`mj_utf8_len`・`mj_utf8_ok` の単体試験**（gcc、AddressSanitizer と UBSan つき）:
   - 正しいと判定: ASCII、`照明箱テス`、`é`（2 バイト）、絵文字（4 バイト）、U+FFFF、空文字。
   - 正しくないと判定: 長すぎる形（C0 AF・C1 BF・E0 80 AF）、サロゲート（ED A0 80）、U+10FFFF 超え（F4 90 80 80・F5…）、単独の続きバイト（80）、文字の途中で終わるもの（E7 85・F0 9F 98・末尾が E6）、FF。
   - 文字の途中で文字列が終わるとき、NUL で止まり、その先は読まない（続きバイトの判定で NUL が先に弾かれる）。
3. **`mj_escape` の試験**: 末尾の壊れた 2 バイトは `??` になる。出力先が小さいときは文字の途中で切らない（5 バイトの枠に `照明` → `照` だけ）。乱数の入力 20 万回（長さ 0〜17、出力先 1〜112 バイト）で、出力がいつも正しい UTF-8・枠をはみ出さない・NUL で終わることを確かめた（失敗 0、ASan の指摘なし）。
4. **試験版（TAP）で `POST /api/settings`**:

| 送った name | 結果 | 保存された名前 |
|---|---|---|
| `照明箱テスト`（18 バイト） | 400 | 変わらない |
| `%FF` | 400 | 変わらない |
| ASCII 18 文字 | 400 | 変わらない |
| ASCII 17 文字 | 200 | そのとおり |
| `%ED%A0%80`（サロゲート） | 400 | 変わらない |
| ひらがな 17 文字（51 バイト、`form_get` で 39 バイトに切られる） | 400 | 変わらない |
| `照明箱テス`（15 バイト） | 200 | そのとおり |

   最後の名前で Chromium（Playwright）から WebSocket につなぎ、status を 5 回受けて 5 回とも `JSON.parse` で `"照明箱テス"` が読めた。切れなかった。`GET /api/dmx` の name も同じ。
5. 400 のときは `goto bad` で、同じ要求のほかの欄も保存しない（前からの動きと同じ）。
